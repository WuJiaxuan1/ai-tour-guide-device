## 3. 架构：一个业务后端，五个职责域，单独 MCP 接入进程

五个域是职责划分，不要求五台服务器。现有 Node 项目后端继续作为业务中枢；小智负责理解语言、选择允许的工具并组织回复。

```text
手机网页 → Nginx HTTPS → 项目 Node API（qixia-guide.service）
                                   ├─ Route：正式路线规则、道路、版本
                                   ├─ Knowledge：讲解、设施、ID、偏好、来源
                                   ├─ Navigation State：行程定位/到达状态（待建）
                                   ├─ Memory：事件和事实统计（待建）
                                   └─ Media/互动：固定素材及团队彩蛋入口

StopWatch语音 → 小智云端 → MCP工具调用 → qixia-mcp 进程 → 同一个项目 API
                              ↑
                   MCP进程主动连接小智的出站 WSS
```

MCP 是调用接口，不是数据库或导航引擎。部署后 MCP 只调用服务器回环 HTTP，无需新增公网入站 MCP 端口。当前网站问答仍是确定性知识检索，MCP 接通不会自动让网页拥有小智文字聊天或与手表共享聊天历史。

## 4. MCP 当前问题：下一位必须先修复，再部署

本轮只整理交接，没有隐瞒问题或将“在线”升级为“验收通过”。以下直接来自当前代码检查：

1. **路线字段未对齐。** `qixia.recommend_routes` 传 `entryGate`，而 `matchPresets` 读取 `gate`，入口筛选会被忽略。`exitGate`、`preferredPlaceIds` 也未被匹配服务消费。应映射已支持字段，不支持的条件明确说明，不能声称已应用全部条件。补真实规则结果测试。
2. **长结果并未可靠控制。** 景点返回嵌套 `place`，`fitPayload` 却只裁顶层 narration；设施返回 `facilities`，裁剪逻辑没有该字段。真实数据可能返回 result_too_large；目录仅截前三条，缺完整翻页。应按UTF-8预算作有效摘要/分页并保留ID、来源、未知状态。
3. **报文预算重复。** stdio同时返回 `content` 与 `structuredContent`，900字节业务对象不代表完整报文在1024字节内；加 truncated 字段后也未重算。按平台实际合同核算输出，不能直接截断JSON或中文。
4. **配置未完全传给子进程。** 管道已修复根 `.env.local` 的查找路径；但仅从文件读取 MCP_ENDPOINT，spawn 仍只传 process.env。文件内 QIXIA_API_BASE_URL 不会自动传给子进程，当前本地默认8787恰好可用。服务器可用 systemd EnvironmentFile 注入18787；本地也要修复配置传递并测试。
5. **故障恢复和输入校验需要补齐。** 管道断线即退出，无内建重连；生产拟靠 systemd 重启。补关闭/重连、WebSocket消息格式、错误脱敏、参数严格校验、超时等测试。当前schema不等于运行时全面校验。
6. **来源、身份与语义要保持真实。** `explain_current_place` 实际依赖显式placeId，不知道游客当前在哪；工具描述的“已审核”尚不能替代完整审核记录。位置参数只是输入，不能当成可信GPS或到访凭证。尚未有会话绑定，不开放用户私有状态工具。

## 5. 没有手表也能推进什么

队友可以先运行后端与自动测试，用本地 MCP 测试客户端通过 stdio 请求 initialize、tools/list、tools/call；不必等待设备。先用真实项目数据验证明镜湖、未知问题、路线入口差异、无匹配和设施查询，再测响应大小和上游错误。保持stdin打开等异步回答，避免一次性管道EOF导致当前程序提前退出。

之后运行 WSS 桥，小智页面看到在线和工具列表只算连接/发现验收。真正语音验收留给持有同一智能体绑定设备的队友：说“请使用栖霞景点讲解工具介绍明镜湖，地点ID是 mirror-lake”。需取得实际工具请求/返回证据，再核对语音内容。当前桥没有完整业务调用审计，不假设控制台一定存在调用日志页；必要时补只记录工具名、成功/失败和耗时的脱敏日志。
