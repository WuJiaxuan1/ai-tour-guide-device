# P9-cloud02：语音配对码同时连接行程和地图

状态：本地实现与自动检查完成；尚未部署到公网、烧录真机或完成语音实测。当前手表 overview02 需要升级。本次不改头像、按键、唤醒词、配网流程或地图绘制协议。

## 游客使用
1. 手表联网，在语音页说“请给我网页行程的配对码”。
2. 在网页“我的路线 → 连接我的枫叶精灵”填入 8 位码。
3. 点击开始游览，手机允许定位并保持网页在前台，手表保持联网。
4. 切到手表地图页，自动接收前往下一站的地图、路线和位置。网页确认到达/跳过后更新下一站。

只保留一个连接卡片，不再下载 stopwatch-navigation.json，也没有单独的“同步到手表地图”分区。卡片显示真实的等待定位、生成地图、等待手表接收等状态；配对成功并不代表地图已显示。刷新页面会向服务器重新读取绑定。

## 原理和接口
- 手表原生 MCP 工具 `self.qixia.get_pairing_code` 提供数字码；秘密领取凭据不返回模型。
- 后台提前 POST `/api/v1/watch/pairings`，返回 pairing_code、claim_token 和 300 秒有效期。若准备未完成，工具明确返回 preparing，提示稍后再查询，不编造码、不阻塞语音主线程。
- 网页沿用 POST `/api/v1/trips/:id/pair-device`，请求 `{code:"8位数字"}`。成功同时绑定云端语音上下文与这块手表。GET 同一路径读取绑定状态及 watch_linked。
- 手表用 `Authorization: Bearer <claim_token>` 查询 GET `/api/v1/watch/pairing`，即使在语音页也能发现绑定。绑定后存入 NVS，重启可恢复，仍需按原流程配网。
- 绑定有效期 12 小时。码只能用一次；重新配对撤销此前已绑定的手表凭据。服务器数据库只存令牌和配对码的散列。
- 领取凭据仅能查询配对状态、访问自己的 `/trips/:id/watch/*` 地图/路线/位置和 ACK，不能读取普通行程接口、调用语音桥接工具或修改游客数据。
- 当前依然是**单智能体、单演示手表的全局绑定**。不宣称支持多游客同时独立使用；多人需要按设备/智能体拆分语音上下文。
- 云端 MCP 工具目录移除原 `qixia_pairing_code`，保留行程问答等工具。兼容旧已绑定的语音状态，界面会明确提示旧绑定仅关联语音。
- 地图继续使用官方高德 JS SDK 渲染、无地图文字、480×480、默认 zoom 14，必要时缩小容纳下一站路线；地图 QMAP v4 和路线 QRTE 分开传输。

## 本地维护人员联调
生产默认地址在 `cloud_navigation.cc` 的 WATCH_SERVER_ORIGIN，可通过编译宏覆盖。只有测试环境换服务器时才需维护人员设置一次 origin：

```powershell
python tools/configure_cloud.py --watch-ip 192.168.x.x --server-url http://192.168.x.x:8790
```

这里第一个 IP 是手表，第二个是电脑。后端须监听电脑局域网地址并允许必要入站连接；浏览器真手机 GPS 通常需 HTTPS 安全上下文。此命令清除手表旧地图绑定后准备新码，**不是游客日常步骤**。正式环境不应使用明文公网 HTTP。旧 --config 参数仅兼容历史维护用途。

## 验收
1. 网页只看到“连接我的枫叶精灵”，没有配置下载或独立同步卡片。
2. 手表给出 8 位码；网页填码后语音回答的下一站与网页一致。
3. 开始游览、取得定位，切到地图页显示正确下一站路线；卡片先显示准备/等待，收到 ACK 后才显示已接收。
4. 刷新网页仍显示绑定；切页、继续对话和头像互动正常。
5. 改变下一站，地图自动更新；暂停后停止有效导航。换行程重新配对，旧手表凭据失效，不显示上次 ACK。
6. 错码、重复码、过期码有错误提示；重启手表并重新联网可恢复未过期绑定。
7. 私密凭据不出现在语音、日志或页面上。
