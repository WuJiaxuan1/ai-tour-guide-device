## 用户反馈与本次处理

用户实物体验发现页面渲染慢、卡顿，并提出将小智提醒改为位置/下一站问答时附带一句。本次按该交互方向处理，不引入主动设备TTS推送。

代码确认的性能负担包括：首屏同时预加载四张背景、全屏动画/滤镜叠加，以及保存选择后还等待整份行程/导航刷新才推进。尚无用户手机性能分析报告，因此这些属于已消除的代码瓶颈，不等于已测出全部卡顿原因或保证目标帧率。

- 小于等于700px的手机布局使用800px宽的WebP衍生图片，原始团队素材保持不变。四张图合计从1,150,744字节降到263,104字节（约77%）；首屏背景从395,212降到82,294字节（约79%）。文件名含内容哈希，可长期缓存。
- 首屏只预加载当前山居图；其余章节按进度提前准备下一张。图片异步解码后替换背景，避免先切空白背景再等待图片。
- 手机端停用全屏颗粒/雾效、场景缓慢缩放及背景模糊，缩短章节过渡；保留故事画面与选择。长按进度改为requestAnimationFrame。环境音跨章节不再无条件暂停后重播。
- 正常选择从GET当前行程→POST选择→等待行程/导航刷新，改为直接用已知版本POST，收到成功结果即推进，导航刷新在后台继续。仅VERSION_CONFLICT时补拉并重试一次；保留事件ID、错误提示和切换行程保护。不在保存失败时假装完成。超过180毫秒显示保存状态，防止连续点击。

## 提问时提醒

服务端 navigation-context 新增 immersive_hint，并在 guidance.location / next_stop / next_leg 中附带；qixia_trip_ask的确定性回答也使用同一提示。即使云端选了读取上下文工具，也能得到包含提醒的参考回答。

触发须为活跃行程、路线含栖霞寺、定位fresh且current_place=temple、体验尚未完成。当前位置仍按连续至少10秒在点位45米内判断，精度不差于60米，定位有效期90秒。支持“下一站是哪里”“接下来去哪里”“下一个景点是哪”“我现在在哪里”“我们在哪”“这里是哪”“现在到哪了”“到下一站还有多久”等。

附加句为：你附近的栖霞寺有沉浸式体验，可以点击网页上的“沉浸式体验”标签进入。

网页点暂不体验只关闭自动弹窗，不屏蔽之后的问答提示；不要求存在pending提醒。已体验一部分可继续得到提示，完成后不再附加。离开、定位过期/低精度、暂停或结束不附加。显式询问体验仍可回答入口。每次符合条件的位置/下一站问答均可附带，没有新增语音去重计时器；需要时可再按产品反馈调节频率。

这是用户提问后的小智回答，不是服务器让设备自动开口。无需刷固件；物理ASR和云端工具选择/口头表达仍需用户验收。
