# 03 总体技术架构

- 文档版本：v1.0
- 状态：团队开发基线（可随实现更新）
- 适用项目：栖霞山随身文旅智能体

## 1. 设计目标

在有限开发周期内，构建可演示、可扩展的旅行智能体原型。系统通过网页和小智语音设备提供交互，围绕景点知识、路线规划、实时行程状态、到访记录、语音笔记和旅行记忆形成闭环。

核心原则：
1. 网页与小智共用同一套业务后端，不重复实现业务规则。
2. 大模型负责意图理解、工具选择和自然语言组织；业务事实、权限校验、状态变更由后端负责。
3. 路线推荐优先使用已核验候选路线与确定性规则；大模型不得自行编造路线。
4. 先实现可测试的普通 API/函数，再按需接入工具调用或 MCP。
5. 计划记录、实际到访记录、用户原话和 AI 摘要必须分开保存。

## 2. 总体架构

```text

  └─ 语音采集 / 服务端语音链路 / 语音播报
       └─ 小智现有语音服务与模型（具体能力待验证）
             └─ 自定义工具调用 / 适配层 ─────────┐
                                                  │
网页端 React + TypeScript                         │
  ├─ 文字输入 / 图文讲解 / 沉浸式景点页面         │
  ├─ 手机定位授权 / 行程状态展示                  │
  └─ 路线偏好表单                                  │
       └─ HTTPS REST API ─────────────────────────┤
                                                  ▼
                                      FastAPI 业务后端
                                      ├─ 对话/意图适配
                                      ├─ 知识检索与景点讲解
                                      ├─ 路线筛选与推荐
                                      ├─ 旅行与行程状态
                                      ├─ 定位与到访记录

                                      └─ 小智工具适配层
                                                  │
                        ┌─────────────────────────┼───────────────┐
                        ▼                         ▼               ▼
                 PostgreSQL/SQLite          知识库文件/索引    地图服务 API
                 业务记录与记忆             讲解/事实/来源      定位/路线/POI
```

## 3. 现成服务与项目自研边界

| 能力 | 现成服务/组件 | 项目必须自行实现 |
|---|---|---|
| 语音采集与播放 | 小智设备及现有语音服务，具体能力需验证 | 与业务工具的对接、错误反馈、会话与旅行上下文映射 |
| ASR/TTS | 优先沿用小智服务端已有能力 | 不重复开发；若现有服务不提供，再评估替代服务 |
| 大模型 | 优先沿用小智现有云端模型；必要时由后端调用模型 API | 工具定义、输入约束、结果校验、业务权限与事实边界 |
| 网页 | React + TypeScript + Vite | 页面、交互、路线卡片、沉浸式景点讲解、行程记录 |
| 后端 API | FastAPI、Pydantic、SQLAlchemy 等框架 | 业务逻辑、状态机、校验、持久化与异常处理 |
| 数据库 | PostgreSQL；早期本地原型可用 SQLite | 数据模型、迁移、备份策略和访问层 |
| 地图/导航 | 高德等地图服务 API 或官方导航跳转 | 将路线与景点 ID 映射到地图服务、展示状态、失败降级 |
| 知识库 | 现有整理好的知识库文件 | 白名单导入、元数据、检索、来源展示、待核验处理 |
| 旅行记忆 | 不依赖外部“记忆型 Agent” | 保存到访和笔记、生成可编辑摘要、查看/修改/删除 |
| 部署 | Docker Compose 等现成工具 | 环境配置、健康检查、日志、上线流程 |

## 4. 端到端实现通路

### 4.1 语音问答与景点讲解
1. 用户对小智说出问题。
2. 小智语音服务完成音频处理/转写/模型请求（实际分工以当前服务配置为准）。
3. 模型识别意图并选择允许的工具，例如 `get_attraction_guide`。
4. 工具适配层调用 FastAPI；后端根据景点 ID 或关键词检索知识库并返回带来源的结果。
5. 模型将结果整理成适合语音播报的短回答；小智播放。
6. 对无法确认的问题，明确告知证据不足，不编造。

### 4.2 网页文字问答与沉浸式讲解
1. 用户在网页输入文字，或从景点列表/地图点击某个景点。
2. 网页调用统一 API。
3. 后端返回讲解内容、图片/媒体引用（若已授权和整理）、来源及核验状态。
4. 网页显示图文讲解、相关景点、资料来源和“开始讲解/继续游览”等操作。
5. 沉浸式体验是前端展示方式，使用同一套景点事实和讲解 API，不单独维护另一份知识。

### 4.3 路线规划
1. 用户选择入口、时长、体力强度、老人/儿童同行情况及 1–2 个必去景点。
2. 前端提交 `POST /api/planner/recommend`。
3. 后端先执行硬性约束过滤，再对符合条件的候选路线评分与排序。
4. 返回 0–3 条已核验候选路线及特点、推荐理由、来源。
5. 大模型可润色推荐说明，但不能修改路线节点、顺序、时长等事实。
6. 用户选中路线后，后端保存为旅行计划。

### 4.4 行中状态、定位与到访
1. 网页在用户授权后读取前台定位。
2. 前端提交坐标、精度、采集时间和旅行上下文。
3. 后端保存必要的位置状态，不默认保存高频轨迹。
4. 用户确认到访后创建 `visit_event`；计划路线与实际到访分开。
5. 后端更新下一站查询所需的行程状态。
6. 需要详细导航时，跳转地图服务；地图导航状态不等于业务到访状态。

### 4.5 语音笔记与旅行记忆
1. 小智语音转写文本后调用 `save_voice_note`，网页也可输入笔记。
2. 后端保存原始文本、时间、来源和关联旅行/景点。
3. 行程结束时，记忆模块读取计划、实际到访和笔记生成摘要草稿。
4. 用户可以编辑、确认、重新生成、导出或删除摘要。
5. AI 摘要不能覆盖原始记录。

## 5. 技术栈建议

- 前端：React + TypeScript + Vite。
- 后端：Python + FastAPI + Pydantic。
- 数据：SQLAlchemy + Alembic；PostgreSQL，开发初期可 SQLite。
- 测试：pytest；前端按项目实际选择 Vitest。
- 部署：Docker Compose（如时间允许）。
- 地图：按可用权限选择高德 Web 服务 API/地图 JS SDK/导航跳转。
- 模型：先沿用小智现有云端模型，优先验证自定义工具调用能力；不要把模型选择作为首个阻塞项。

## 6. 部署与环境边界

- API 密钥仅保存在服务端环境变量中，不提交到 Git。
- 开发、测试、演示环境使用不同配置。
- 地图 API 的浏览器端 Key 与服务端 Key 按供应商安全要求分别管理。
- 数据库变更通过迁移脚本管理。
- 本地启动方式、必需环境变量和健康检查应在 README 中维护。

## 7. 关键架构决策

1. 后端是业务状态的唯一权威来源。
2. 小智和网页是两种交互入口，不是两套业务系统。
3. 路线推荐首版使用可解释的规则算法。
4. 知识检索首版可用关键词/结构化查询，不强制引入向量数据库。
5. 不在首版实现自动到访判定、高频轨迹、复杂多 Agent 编排。
