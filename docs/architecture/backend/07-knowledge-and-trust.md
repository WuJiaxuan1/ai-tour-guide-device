# 07 知识库与事实可信度规范

> 2026-10-31 实现校正：本地已在现有 Node/React 项目接入五模块基础链路。实际接口、字段、模型供应商、验证结果与未完事项以 [11-implementation-20261031.md](11-implementation-20261031.md) 为准；本文件其余未落地条目保留为目标设计，不代表已部署。

## 1. 目标

确保景点讲解、路线推荐和运营提示基于可追溯资料，避免模型将推测、过期信息或用户计划说成事实。

## 2. 知识库分层

| 类型 | 内容 | 使用方式 |
|---|---|---|
| 结构化事实 | 景点 ID、名称、坐标、路线节点、时长、设施等 | 优先由数据库/结构化文件查询 |
| 讲解文本 | 景点历史、文化、自然景观介绍 | 检索后用于回答与沉浸式讲解 |
| 动态运营信息 | 开放时间、临时封闭、交通、服务状态等 | 必须标注更新时间和核验状态 |
| 待核验材料 | 缺少证据、冲突或过期的内容 | 仅用于人工核验，不作为确定事实回答 |
| 原始材料 | 原始采集、未整理资料、内部材料 | 不进入 RAG/生产索引 |

现有知识库目录包括 `00_路由与规范` 至 `09_待核验与证据`，以及 `90_原始材料_禁止上传到RAG`。实际导入策略以当前仓库文件为准。

## 3. 强制排除规则

- `90_原始材料_禁止上传到RAG` 必须通过目录白名单或明确路径规则排除。
- 不可只靠模糊文件名匹配来排除。
- 导入器应在运行日志中报告扫描数、导入数、跳过数、失败数和待核验数。
- 对被排除目录中的文件增加自动化测试，确保不会被索引。
- 未被明确允许的目录默认不导入（白名单优先于黑名单）。

## 4. 来源与元数据

每条可检索内容尽可能保存：
- `source_id`：稳定来源 ID。
- `source_path`：相对文件路径或数据库记录。
- `title`：标题。
- `content_type`：fact/guide/operation/faq/route/unverified。
- `verification_status`：verified/unverified/outdated/unknown。
- `verified_at`：最后核验时间。
- `updated_at`：内容更新时间。
- `evidence_note`：核验说明。
- `attraction_id` / `route_id`：适用景点或路线（若有）。

## 5. 回答策略

1. 优先检索结构化事实和已核验资料。
2. 动态信息若过期或无核验时间，应提示“信息可能变化，请以景区现场公告为准”。
3. 证据不足时说明无法确认，必要时询问用户补充信息。
4. 多个来源冲突时，不自行选择一个当成确定事实；返回冲突或标记待核验。
5. 不得根据常识补造栖霞山具体路线、开放状态、距离、坡度或设施情况。
6. 模型生成的文字必须与检索结果分离存储，且保留来源 ID。

## 6. 行中讲解规范

- 小智语音问答与网页沉浸式讲解共用同一套检索与事实接口。
- 语音回答优先简洁、适合口头收听；网页可展示更完整正文、图片和相关景点。
- 网页沉浸式页面可有叙事、分段、图片和交互设计，但不能因此引入未经核验的新事实。
- 图片、音频、视频素材必须确认来源与使用权限。
- 讲解页面应显示可用的来源或“资料核验状态”，不必将内部检索技术暴露给游客。

## 7. 路线数据质量要求

每条用于正式推荐的路线至少具备：
- 唯一 ID、名称、入口/出口。
- 有序景点列表。
- 预计时长及其来源/估算方法。
- 体力强度标签和标签依据。
- 老人/儿童适配信息；未知必须存为 unknown/null。
- 路线状态及最后核验时间。
- 来源引用。

只有 `verification_status = verified` 且状态可用的路线才能作为正常推荐候选。若无合适路线，应返回不足，不得为凑数放宽硬约束。

## 8. 检索与索引策略

MVP 可使用结构化查询、关键词检索或全文检索。只有当数据量、召回率或同义表达需求证明必要时，再增加向量数据库。
- 每次索引重建记录版本与导入摘要。
- 同一来源重复导入应幂等。
- 删除或更新来源时，应同步更新相关索引。
- 检索结果应能追溯至源文件/条目。
