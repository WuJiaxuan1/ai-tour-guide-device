## 分层与目录建议

五个业务域可以先作为一个 Node.js 后端内的模块，不需要拆成五台服务器或五套数据库。

| 层 | 职责 | 位置 |
|---|---|---|
| 项目 API / 会话 | 校验身份、参数、行程归属，协调业务模块 | 现有 `backend/src/`，增量整理 |
| Route | 正式筛选、版本、路线快照和可导航校验 | 现有 `presets.mjs`、`backend/data/routes/` |
| Navigation | 位置质量检查、路线匹配、下一站、到达候选 | 待新增后端状态模块 |
| Knowledge | ID、来源、版本、证据检索 | 现有 `knowledge.mjs` 和 `backend/knowledge/` |
| Memory | 结构化事件、事实统计、摘要 | 待新增；持久数据放服务端数据目录，独立于发布目录且不进入Git |
| Media / 互动内容 | 固定图片、下载、审核页面入口 | 现有前端素材和团队交付页面；本次Demo无需图片生成进程 |
| 京东云适配 | 网页文字回答；后续按事实摘要生成表述 | 建议 `backend/src/providers/jdcloud.mjs`，尚未创建 |
| 小智 MCP 适配 | 将允许的业务查询包装为工具 | 建议 `backend/integrations/xiaozhi/`，尚未创建 |

推荐网页链路：网页 → 项目API → 检索/规则/受权行程上下文 → 京东云组织回答 → 项目API校验输出 → 网页。

推荐语音链路：手表 → 小智云端 → MCP桥接工具 → 项目API → 结构化结果/知识证据 → 小智语音回答。

两条链路共享业务事实；不假设自动共享聊天历史。小智仍使用原有语音模型，京东云作为网页文字通道的补充。MCP接入地址不是网页聊天接口。语音知识工具首版直接返回证据，避免每次小智调用再套一层京东云。

模型不直接读写数据库，不生成正式路线，不决定到访或改写统计数字。若模型参与意图提取，结果仅作为待校验参数；用户确认路线后由后端写入。不要把来源ID引用误当作已全面保证生成事实正确，需保留证据不足和失败回退。

## 实施顺序与验收

1. **整理共同业务合同和知识证据。** 沿用现有Node后端与API，统一景点ID、来源/版本、路线三态及缺资料规则。保留审核状态，过滤私人来源路径。先用明镜湖讲解、无资料问题、情侣/闺蜜偏好和无匹配路线验收；不要求新建向量库。
2. **打通知识问答的两条入口。** 实现京东云适配及小智只读知识工具。先本地模拟超时、鉴权失败和异常响应，再配密钥做一条非敏感问题的真实调用；手表确认真实工具调用。网页与手表都回答同一知识问题，核对来源。可先验收一个入口再做另一个。
3. **建立行程与绑定。** 后端创建匿名会话和trip，保存路线ID/版本快照、开始/结束状态。tripId只是标识，不是访问凭证。演示可从一台手表绑定一个活动行程开始，绑定由受权服务端上下文确定；工具不能任意指定别人的trip。随后开放当前行程、下一站等工具。
4. **导航状态与硬件联调。** 网页GPS上传坐标系、精度、时间、序号，服务端检查过期/乱序/不合理跳变并按已确认路线几何计算。服务器计算不能证明浏览器GPS绝无伪造，自动判定与手动确认分别记录来源。先验证单条资料完整路线，再对接手表显示与路线版本确认。地图图像已有接收/显示协议，不等于已有routeId/revision的路线ACK。
5. **事件与记忆闭环。** 在第3步建事件基础，在本步完善到访、询问、收藏等事件与幂等统计。模型只组织文字。演示报告继续使用单独的固定配置值；真实事件统计与预设数值分开标记，不把预设公里数/时长描述为实测。
6. **演示呈现与整体验收。** 贴纸为固定原图/成品上下对比，选择照片仅本地预览，无在线生成。接入团队完成的互动页面，小智仅提示入口。最终验证弱网、精度不足、版本变化、未连接与模型失败；之后部署，Git提交/推送按用户后续授权执行。

硬件现状仍为Android前台向手表发送地图/位置，切后台或锁屏会停止同步。网页与App不能默认同时提供可互换的权威位置源；行程应约定来源及切换规则。会议希望纯网页，不代表现有固件已能摆脱Android。该差异需在第4步明确并联调，不能仅靠文档宣称解决。

## 京东云配置时机

现在可以准备账户及API Key、选择账户实际可用的模型。先实现适配层并通过本地检查，再填入Key做小规模联调；不必等导航、报告全部完成。

以下为**拟新增配置**，现有 `backend/src/config.mjs` 只读取高德字段，目前直接填写这些变量不会接通模型：

```dotenv
TEXT_MODEL_PROVIDER=jdcloud
JDCLOUD_CHAT_URL=https://modelservice.jdcloud.com/v1/chat/completions
JDCLOUD_MODEL=
JDCLOUD_API_KEY=
JDCLOUD_TIMEOUT_MS=20000
MCP_ENDPOINT=
```

- `JDCLOUD_MODEL`：原始文档列出 `DeepSeek-V4.1-Flash-1017`、`Kimi-K2.5`；Kimi在表格和示例中重复一次，并非第三种模型。这些是用户文档中的名称，账户可用性尚未实测。
- `JDCLOUD_API_KEY`：由用户在本机或服务器私有配置中填写，不发聊天。开发可沿用Git忽略的根目录 `.env.local`；生产使用发布目录之外的服务端环境文件/进程环境。公开 `.env.example` 只放变量名和非敏感默认值。
- 后端按文档发送 `Authorization: Bearer …`、`Content-Type: application/json` 和每请求新生成的 `Trace-Id`，首版使用 `stream:false`。不能给秘密变量加 `VITE_` 前缀或打包进前端。
- MCP桥接是独立进程，需单独注入 `MCP_ENDPOINT`；Node配置文件不会自动传给Python子服务。日志遮盖令牌和URL查询参数；stdio标准输出只用于协议。
- 原始文档没有响应JSON、错误码、限流/额度、消息角色约束、工具调用或流式事件说明。首版只按非流式文本接口验证，不据此承诺完整兼容某SDK或function calling。
- 根据真实响应实现严格解析、超时、有限历史长度和重试边界。异常时显示可重试状态或明确使用已有知识检索结果，不能返回伪造的模型成功。
- 小智说明提示工具结果通常有限额，先以1024 UTF-8字节为保守预算；结果编码后校验，不能直接截断JSON或中文字符。完整道路几何不走语音工具结果。

### 2026-10-31 MCP 接入合同

小智控制台提供的接入点格式为 `wss://api.xiaozhi.me/mcp/?token=...`。该地址本身包含私有 token，不能写入 Git、前端或聊天。项目已新增 `backend/integrations/xiaozhi/`：本地 stdio MCP 服务把已验证的后端查询包装成只读工具，再由 `mcp_pipe.mjs` 转发到 WSS 接入点。

首批工具为 `qixia.explain_current_place`、`qixia.search_knowledge`、`qixia.recommend_routes`、`qixia.get_route_catalog` 和 `qixia.get_facilities_nearby`。工具返回保留来源、路线三态和 `navigationReady`，结果按约 900 UTF-8 字节控制；不暴露 GPS 写入、到访确认、记忆写入或自由路线生成。

本机配置根目录 `.env.local`：

```dotenv
MCP_ENDPOINT=wss://api.xiaozhi.me/mcp/?token=本机真实token
QIXIA_API_BASE_URL=http://127.0.0.1:8787
```
