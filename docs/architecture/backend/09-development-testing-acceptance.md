# 09 开发、测试与验收规范

> 2026-10-31 实现校正：本地已在现有 Node/React 项目接入五模块基础链路。实际接口、字段、模型供应商、验证结果与未完事项以 [11-implementation-20261031.md](11-implementation-20261031.md) 为准；本文件其余未落地条目保留为目标设计，不代表已部署。

## 1. 开发原则

- 先确认接口与数据模型，再并行实现模块。
- 每次只开发一个可验收的小任务。
- 不在一个任务中同时大改架构、重写知识库和新增多个业务模块。
- 修改公共 API、数据模型或状态定义前，先同步相关负责人并更新文档。
- 代码由负责人完成后，至少经过一次集成检查。

## 2. 推荐仓库结构

```text

│   │   └── main.py

```

按实际项目调整，但不要让多名成员各自建立互不兼容的目录结构。

## 3. 编码约定

- Python 使用类型注解；请求/响应使用 Pydantic schema。
- 路由层只处理 HTTP、参数验证和响应；业务逻辑放在 service 层。
- 数据库访问集中在 repository/model 层。
- 前端请求集中封装 API client；不要在组件里重复写不同的错误处理。
- 枚举值与 API 文档一致。
- 配置从环境变量读取；提供 `.env.example`，不提交真实 `.env`。
- 日志避免输出密钥、完整定位和不必要的个人数据。
- 新增依赖前说明用途，避免为简单功能引入大型框架。

## 4. 分支与提交

建议每个模块负责人使用独立分支或独立 PR。
- 提交前运行格式检查、类型检查和测试。
- 提交说明采用清晰前缀，如 `feat: add route recommendation`、`fix: prevent duplicate visits`、`docs: update API contract`。
- 不盲目执行 `git add .`；检查差异，确认未提交密钥、数据库文件或原始材料。
- 代码合并前检查公共接口与文档是否同步。

## 5. 测试层级

### 单元测试
- 路线过滤/评分规则。
- 旅行状态机与下一站计算。
- 知识检索来源与证据不足分支。
- 笔记/到访幂等处理。
- 记忆摘要的输入事实边界。

### API 测试
- 正常请求。
- 参数缺失/非法枚举。
- 资源不存在。
- 无权限访问。
- 外部服务超时。
- 重复提交。
- 无符合条件的路线。

### 集成测试
- 创建旅行 → 保存路线 → 开始旅行 → 确认到访 → 查询下一站。
- 创建语音笔记 → 结束旅行 → 生成摘要草稿 → 编辑/确认。
- 网页景点讲解与小智工具查询返回同一套知识来源。

### 手动演示测试
- 手机网页授权定位与拒绝定位两种路径。
- 小智工具不可用时，网页核心功能仍能运行。
- 知识库中不存在的问题不会得到虚构的确定答案。
- 沉浸式景点页在媒体缺失时仍可显示文字。

## 6. 核心验收清单

### 知识库与讲解
- [ ] 可列出、搜索和查看景点。
- [ ] 讲解结果包含来源/核验状态。
- [ ] `90_原始材料_禁止上传到RAG` 被明确排除并有测试。
- [ ] 证据不足时不编造。

### 路线规划
- [ ] 表单支持入口、半天/全天、体力、老人/儿童、最多两个必去点。
- [ ] 后端返回 0–3 条符合硬约束的已核验路线。
- [ ] 不为凑足三条而放宽硬约束。
- [ ] 用户选择后才保存为旅行路线。

### 行程状态
- [ ] 可创建、开始、暂停、恢复和结束旅行。
- [ ] 下一站基于后端保存状态计算。
- [ ] 计划与实际到访分开。
- [ ] 重复提交不会产生重复到访事件。

### 记忆
- [ ] 可保存语音转写/文字笔记。
- [ ] 可生成摘要草稿并由用户确认。
- [ ] 摘要生成失败不影响原始数据。
- [ ] 可查看、编辑、删除摘要。

### 前端与小智
- [ ] 网页提供文字输入、图文景点讲解、路线选择和行程操作。
- [ ] 小智至少验证一个只读工具调用；目标是三项工具。
- [ ] 同一业务请求在网页和语音端的结果一致。
- [ ] 无权限、超时和无数据均有明确反馈。

## 7. 本地启动与 CI

README 至少应包含：
- 安装依赖的命令。
- `.env.example` 复制方式。
- 数据库初始化/迁移命令。
- 导入知识库命令。
- 启动前端和后端命令。
- 运行测试命令。
- 健康检查地址。

建议后端每次提交运行 `pytest`；如时间允许，CI 中加入 lint、类型检查和前端构建。
