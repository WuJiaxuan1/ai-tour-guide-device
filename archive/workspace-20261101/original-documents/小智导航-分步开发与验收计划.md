# StopWatch 小智＋周边地图：分步开发与验收计划

更新日期：2026-10-28。本文是开发计划，各阶段实际状态见文末进度表；不能将离线检查当作真机通过。

## 一、第一版要完成什么

- 以干净的、适配 StopWatch 的 M5Stack 小智源码为基础，优先保证语音稳定。
- 保留原有小智设备身份和云端绑定；首次刷入后实际验证。清理 Wi-Fi 不等于清理绑定。
- 每次开机清空旧 Wi-Fi 列表，进入热点配网；本次运行允许保存密码和自动重连。不做仅内存保存密码的额外改造。
- 语音页用“枫叶精灵”唤醒；需要正确打包配套模型并真机验证。
- 每次开机将音量设为 85（0～100），本次运行可调节，下次开机再次恢复 85；该需求在 P5 新增。
- 左侧语音页、右侧地图页。短按左键或右滑回语音，短按右键或左滑进地图；处于对应边界时不切换。使用 LVGL 平移动画，暂不新增左键长按功能。屏幕滑动需求在 P6 新增。
- 两页先互斥工作：地图页停止语音录制、播放和唤醒；语音页停止持续地图绘制及不必要的大数据传输。保持 Wi-Fi 连接。
- 地图页仅显示手机周边地图和当前位置，随移动更新，第一版北朝上。
- Android App 复用 MotoNav 的定位、地图处理及编码逻辑，新增 Wi-Fi 通道，通过 Zenfone 10 热点局域网发送数据。
- 不要求目的地、路线、转向、天气、音乐、水平仪、地图旋转，也不要求自建服务器、MCP 地图传输或网页端。

## 二、协作规则

1. 一次交付一个可解释、可验证的小成果；每次附版本号、改动说明、安装方法、测试步骤和已知问题。
2. 助手完成代码检查、可执行的编译和协议测试后，再交给用户真机验收。不把“编译成功”当作“设备可用”。
3. 用户反馈“通过”或具体问题后，记录结果。依赖该结果的功能在验收后推进；等待时可做文档、接口定义等不依赖结果的工作。
4. 每阶段保留上一可用版本和配套配置。出现回归，先定位；需要时恢复上一可用版本，不连续叠加未经验证的修改。
5. 用户负责设备操作与实测，助手负责代码、构建、日志分析和修复。不要求用户先学完整套硬件开发。
6. 首次刷写前给出明确目标设备、固件、写入范围和恢复步骤；现场确认设备连接情况。不把安装环境或生成固件等同于已经烧录。
7. 不改动现有 MCP 演示工程；原有 Grok 工程保留参考，融合版本使用独立源码目录。工具链经过核对后可以复用。
8. 运行状态与验收记录区分“未开始、开发中、待真机验收、通过、待修复”。

## 三、阶段与验收

### P0：确认现状、验证环境与恢复方式

助手工作：
- 记录当前可用固件的名称、来源和版本；若无法读出，明确记录未知，不猜测。
- 确认小智干净基线源码版本、StopWatch 板型、分区和依赖版本。
- 运行验证 ESP-IDF、编译器、配套 Python、JDK、Gradle、Android SDK、ADB 等工具。优先使用已存在的工程工具链，不盲目升级或修改系统 PATH。
- 检查现有备份和恢复流程的适用性。历史备份不自动等于当前状态，恢复须核对板型、布局和固件版本，不公开其中的私有配置。
- 建立独立源码、发布包及测试记录位置，记录原始版本和后续改动。

用户操作：
- 告知目前设备是否正常小智对话、是否仍绑定原智能体。
- 连接设备和手机的数据线，按需允许 USB 调试；测试 Wi-Fi 与热点是否能同时开启，并报告系统实际行为。

交付与通过标准：环境检查记录、基线选择、可执行的恢复说明；明确能否进入构建阶段。路径存在但未运行的工具不能标为已验证。

### P1：干净小智基线与 Android 构建基线

助手工作：
- 构建未加入融合功能的小智固件，提供明确的安装和串口日志采集方式。
- 构建 MotoNav Android 开发 APK，核对对应源码版本及 StopWatch 适配版协议差异。
- 配置独立测试应用标识或安排明确安装方案，避免意外覆盖已有可用 App。应用标识与签名确定后，再配置匹配的高德 Key。
- 固件使用兼容的配置保留方案，避免全片擦除；检查云端自动升级行为，防止后续测试版意外被替换。

用户测试：
1. 小智能配网、联网、唤醒并完成连续三轮对话。
2. 云端仍显示原设备与预期智能体；若要求重新激活，保留日志并报告，不把它算作绑定保留成功。
3. 手机能安装并启动开发 APK。此时不要求 APK 已经能够连接融合固件。

交付：P1 固件、APK、构建记录、恢复方法。
通过标准：基线可重复构建；语音真机正常；绑定结果明确；APK 可启动。

### P2：尽早验证手机热点局域网链路

目的：在移植地图之前确认选定的通信方式可行。

助手工作：
- 设备加入最小测试接收接口，手机加入手动填写设备 IP、连接和发送测试消息的入口。
- 先采用设备作为局域网服务端、手机 App 主动连接的方式；具体使用 WebSocket 等协议在实现时固定，并记录版本。
- 设备收到数据返回确认，双方记录序号和时间。此时不接入真实地图，也不宣称地图已完成。
- 不硬编码手机热点网段；设备显示或通过串口输出实际 IP。

用户测试：
1. StopWatch 连接 Zenfone 热点。
2. App 连接设备 IP，发送十次测试消息，查看每次确认。
3. 同一热点下，小智能联网对话。
4. 关闭、重新开启热点后，设备能重连；App 必要时更新 IP 后重新连接。

通过标准：双向收发与重连可用，且不破坏小智基本联网。先不要求地图与语音同时传输。
失败处理：先查地址、热点本地访问、App 网络策略及系统限制；如果确认该手机不适合此链路，再给出 BLE 等替代方案的具体取舍，不静默更改主方案。

### P3：每次开机重新配网

助手工作：
- 仅在启动阶段清空旧 Wi-Fi 列表，沿用小智原有配网和本次运行的重连机制。
- 保留设备身份配置，避免在普通重连中重复清空。
- 检查配网提交是否会重启，避免“保存后重启又清空”的循环。
- 支持手机热点暂未开启时手动填写网络，设备留出等待手机切换的机会。

用户测试：
1. 关机再开机：即使旧热点可用，也进入配网。
2. 同一部手机完成配网后切为热点：设备能连上。
3. 本次运行关闭、重开热点：设备能自动重连，不再次要求配网。
4. 再重启：再次进入配网；小智绑定仍保持。

通过标准：上述流程连续重复三次，没有配网循环或绑定变化。

### P4：“枫叶精灵”唤醒

助手工作：启用已有自定义唤醒实现，加入匹配的中文模型和命令配置；检查资源打包、加载日志、内存余量和阈值。

用户测试：
- 安静环境约半米处，正常音量说“枫叶精灵”十次，每次间隔并结束上一轮交互；记录成功次数。
- 再测试约一米距离和普通背景噪声，记录结果，不把它们当作统一实验条件。
- 正常交谈或播放背景声音五分钟，记录误唤醒情况。
- 完成至少三轮对话，确认模型变化没有破坏录音播放。

通过标准：演示环境半米距离建议达到至少 9/10 次唤醒，五分钟观察内无频繁误唤醒；该样本仅用于演示验收，不代表产品级识别率。未达标则调整后重测，不提前承诺模型效果。

### P5：双页面、左右键与语音启停

助手工作：
- 添加语音和地图占位页，用 LVGL 实现左右平移。
- 进入地图页时结束当前语音交互、停止录音播放和唤醒；回到语音页恢复唤醒。
- 集中管理页面状态和异步回调，避免语音回调把地图页覆盖。
- 保留必要系统操作，暂不新增左键长按功能。

用户测试：
1. 左右切换二十次，按边界键不出现多余页面。
2. 语音页正常唤醒；地图页说唤醒词不启动对话。
3. 播放回答中切地图页：播放停止且无异常；返回语音页可重新唤醒。
4. 联网不因切页中断，不需要重新配网。

通过标准：显示、按键及语音状态一致，无死机、意外跳页或残留播放。地图页此时仍可只是明确标注的占位页。

### P6：单张测试图传输、绘制与触摸切页

助手工作：
- 固定测试图协议：版本、合成图类型、图像编号、会话、RGB565LE 格式、240×240 尺寸、长度、CRC32、接收/显示确认和失败处理。
- 手机生成 A/B 合成测试图，通过 Wi-Fi 上传，设备完整接收校验后接入 LVGL；本阶段不含地理数据，地图覆盖范围、坐标系和位置时间在 P7 接入真实地图时联合定义。
- 测试图明确标注“非真实地图”，不要求定位权限和高德 Key。真实地图处理代码复用在 P7 落地。
- 新增横向触摸切页：左滑进地图，右滑回语音，与按键共用页面及语音状态控制；轻点、竖滑不换页。
- 设置数据长度上限和缓冲区预算，接收完整后再换图；旧地图与新位置不能错误组合。

用户测试：手机发一张图，设备显示；重复发送和中途断开，检查是否花屏、卡死；切回语音页确认仍可对话。

通过标准：地图完整、方向和颜色正确；失败有提示；中断后可以恢复，不显示半张新图或错误定位点。

### P7：真实周边地图与定位跟随

助手工作：
- 接入匹配应用标识和签名的高德配置、权限与实际定位数据。
- 保留定位与地图必需依赖，关闭路线、电子眼及其他不需要功能；不强行搬入完整高德巡航业务。
- 统一地图和定位坐标系，第一版北朝上。
- 位置小数据按定位回调和限流策略更新；地图仅在覆盖范围不足等条件下更新，不每次定位都发送整屏。
- 返回语音页暂停重传和绘制；再次进入地图页获取新位置，缓存过期时提示。
- 处理定位未就绪、精度较差、定位过期、网络断开、地图加载失败等状态。

用户测试：
1. 室外开阔位置等待真实定位，核对地图是否对应实际附近区域。
2. 步行约 100～300 米，定位点与实际位置合理一致；经过地图更新边界时仍正常显示。
3. 停下时无明显地图乱转；实际定位抖动与程序错误分开记录。
4. 切语音、完成一轮对话，再返回地图，位置更新到当前位置。
5. 关闭定位或断开 App：设备显示等待或过期状态，不假装仍在实时跟随。

通过标准：真定位、真地图、更新链路闭环成立，定位误差结合手机报告的精度判断。走动测试以观察数据为主，不要求边走边操作设备。

### P8：完整演示与稳定性验收

助手工作：修复前序回归；整理演示版固件、APK、构建来源、配网图文步骤、已知限制和恢复方法。

用户完整流程：
1. 开机重新配网，进入语音页。
2. 说“枫叶精灵”，完成三轮对话。
3. App 开始发送周边地图，右键切地图。
4. 步行观察位置变化，左键回语音，再次唤醒。
5. 连续运行至少三十分钟，累计切页二十次。
6. 测试热点中断恢复、App 关闭重开、手机锁屏后五分钟的位置更新情况。
7. 再次关机开机，验证重新配网与原有绑定。

通过标准：完整演示无崩溃或必须刷机才能恢复的故障；普通断连可恢复。锁屏更新如未通过，应先处理前台定位服务、权限和系统电池策略；若暂时仍有问题，只能明确标注为“手机 App 保持前台的演示版”，不能宣称后台定位已完成。

## 四、每次交付包的内容

- 版本与阶段：例如 P5-test01。固件和 APK 分别记录版本；注明兼容组合，避免装错版本。
- 本次新增内容及已知限制。
- 必要的固件、APK、烧录偏移或安装步骤。模型和资源需要同时更新时明确说明。
- 助手已完成的检查及结果；未运行的检查明确列出。
- 用户需要执行的编号测试，通常控制在三到五项。
- 日志采集方式，上一可用版本及恢复步骤。

默认先按单设备开发调试，不把自动发现、批量游客设备管理、账号会话隔离或服务器部署混入第一版。

## 六、职责与排期

助手：源码分析、接口设计、代码修改、工具链验证、构建打包、自动检查、故障诊断、版本记录和说明文档。

用户：USB 连接与授权、账号和手机设置、真机安装配合、语音与走动测试、验收反馈。

依赖顺序：P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8。P2 尽早消除通信风险；P4 在地图重工作之前消除唤醒风险。等待真机反馈时，可准备后续协议与文档，但不把未验收功能标为通过。

先不承诺固定完成日期。P1、P2、P4 完成后，根据真实构建速度、手机链路和唤醒效果，再估计地图移植和稳定性修复时间。
