# 栖霞山枫叶精灵：项目梳理（讨论要点）

> 来源：项目负责人与Claude的讨论整理。标注“待验证”的内容需要现场访谈或实测确认。

---

## 一、比赛信息

- 活动：南京首场AIGC文旅黑客松“枫客松”（栖霞山）
- 形式：48小时，线下，约30支队伍
- 目标赛道：**赛道二：栖霞山文旅智能体开发**
  - 行前：帮游客规划路线
  - 在场：懂景、会讲、能带路
  - 游后：留下可延续的记忆
- 海报强调：**从游客真实需求出发，进行用户调研**，做一个能带人、懂景区、解决问题的AI智能体
- 奖项：全场大奖、赛道一等奖、智能体孵化奖、官方共创奖

---

## 二、项目一句话

一个随身的栖霞山AI旅行伙伴：出发前帮你排路线，路上陪你聊、给你讲，根据你的状态随时调整，走完帮你留下一份旅行回忆。

**核心定位：** 项目的核心是**智能体**（规划、讲解、动态调整、记忆），机器人只是它的实体入口。

**自检问题：** 把机器人拿掉，只剩手机网页，智能体还成立吗？如果成立，方向就没问题。

---

## 三、整体评价

**优点**
- 行前、游中、游后三段与赛道要求一一对应
- AI只从验证过的路线中选择，避免编造路线
- “根据游客状态当场重新规划”能体现真正的智能体能力
- 形象有IP和纪念品延展空间

**主要风险**
- 范围偏大，硬件容易拖慢进度
- “为什么不用手机”会被追问，需要有访谈原话支撑
- 现场网络、户外噪声、设备联调都可能出问题

---

## 四、已确定的方向

1. 做赛道二的文旅智能体
2. 实体载体**直接用小智（开源ESP32语音助手）**，不自研硬件
3. 设备选型倾向 **M5Stack StopWatch**（圆形AMOLED触控屏、麦克风、扬声器、震动、挂绳孔、磁吸）
4. **语音是必须有的**，其他功能都可以降级
5. 路线只从预设数据中选，不让模型自由生成
6. 不使用摄像头，照片由游客主动选择，降低隐私风险
7. NFC**不是核心**，基础版用二维码或按钮确认到达，NFC作为加分项

---

## 五、架构

```text
游客语音
   ↓
枫叶精灵设备（小智固件）：语音、表情，可选震动与箭头
   ↓ 通过MCP或接口
AI后端：路线规划、景点问答、动态调整、旅行总结
   ↑
手机网页：GPS、轨迹、扫码确认到达、旅行卡片
```

| 部分 | 职责 |
|---|---|
| 设备 | 听、说、表情，加分项：震动、箭头、NFC |
| 手机 | GPS导航与轨迹、扫码、旅行卡片 |
| 后端 | 路线规划、景点问答、重新规划、记录与总结 |

**游后回忆**：根据GPS轨迹、到访打卡、对话记录和游客主动选择的照片生成。

---

## 六、分层交付

1. **保底版**：手机网页加后端，完整走通规划、讲解、重新规划、旅行卡片
2. **标准版**：接入小智，实现语音问答与表情
3. **加分版**：震动提醒、简单箭头、NFC打卡、外壳精修

每升一层之前，确认上一层可稳定演示。

---

## 七、核心演示场景

> “你只剩40分钟，还带着老人，精灵当场重新规划路线。”

路演只讲这一个场景，让评委看到感知、规划、调整的闭环。

---

## 八、团队与分工（四人）

| 角色 | 主责 |
|---|---|
| 算法同学 | 路线与景点数据化；规划和重新规划的规则与算法；约束大模型只能选预设路线；评估稳定性 |
| 系统同学 | 后端服务、景点知识库与问答、对话和到访记录、旅行总结、小智/手机端/后端联调 |
| 硬件同学 | 买板（建议备份一块）、烧录小智、配置“枫叶精灵”角色、户外音量与收音实测、外壳；有余力做震动、箭头、NFC |
| 负责人 | 用户访谈、定人群与痛点、角色与卡片视觉、进度与风险、路演稿与备用视频、手机网页的需求与验收 |

**缺口：** 手机网页和视觉设计没有专人。建议负责人牵头，用AI编程工具生成简单页面，系统同学负责接口对接；页面只保留：开始游览、显示路线与位置、扫码或点“我到了”、查看旅行卡片。

### 系统与硬件的边界

- **硬件**：板子、固件、Wi-Fi、音量、麦克风、外壳；小智账号与角色配置；在小智平台上注册和配置工具入口；设备端震动、表情、按键
- **系统**：后端服务与公网可访问；按约定格式提供工具接口，返回内容短、适合朗读；知识库、记录、总结；手机端对接
- **共同**：赛前一起写一页**接口约定**（工具列表、输入输出示例、返回文字风格、出错处理），并坐在一起跑通一次完整调用
- **排查顺序**：先直接请求后端 → 再看设备是否发出请求并收到结果 → 两边都对但效果不好，共同调提示词和返回内容
- **工作量平衡**：硬件同学在设备跑通后，可分担知识库整理、部分接口、联调测试和备用视频

### 互相备份

| 主责 | 备份 |
|---|---|
| 算法 | 系统（接口、数据整理） |
| 系统 | 算法（后端逻辑） |
| 硬件 | 系统（联调接入） |
| 负责人 | 算法或系统（访谈、材料整理） |

## 九、时间线（48小时）

| 时间 | 任务 |
|---|---|
| 赛前 | 买板、烧录小智、试一个自定义工具；整理景点资料；搭后端框架；准备访谈提纲；向主办方确认评分标准、网络、电源 |
| 0–6h | **现场访谈8–10人**；定最终人群、痛点和3个景点、1–2条路线；语音对话跑通 |
| 6–20h | 规划与问答稳定；后端接入语音；手机网页初版；开始写路演稿 |
| 20–30h | 动态重新规划反复测试；旅行卡片；外壳与加分项 |
| 30–36h | 轮流休息，缓冲 |
| 36–44h | 完整彩排，修bug，录备用视频 |
| 44–48h | 冻结功能，只改路演和现场问题 |

**检查点**：约6h访谈完成并定方向；约20h保底版走通；约30h小智联调成败（失败则降级）；约36h全流程彩排；44h后不加新功能。

## 十、用户调研

**目标**：现场访谈8–10人，其中独行游客至少4–5人；记录原话，路演时引用。

**建议问题**
1. 一个人逛景区最不方便的是什么？
2. 你平时怎么解决（地图、讲解、问人）？
3. 如果景区借你一个会说话的小挂件陪你逛，你愿意吗？为什么？
4. 你更想要它讲故事、带路还是陪聊？
5. 更愿意拿一个小玩偶，还是挂在包上或戴在手上的挂件？
6. 愿不愿意保存今天的轨迹和照片？对位置数据有什么顾虑？

**待验证的关键假设**
- 主打人群：独自出行的游客（备选：亲子家庭、老人）
- 游客是否愿意携带实体伙伴，形态偏玩偶还是挂件
- 最想要的是带路、讲故事还是陪聊

---

## 十一、最难的部分与风险

1. **小智与后端联调**（最大技术不确定点）：官方服务器上注册自定义工具的具体步骤尚未核实，拿到板子后第一时间实测；不通就让手机端承担主要功能
2. **让“现场重新规划”真实可信**：路线数据要自己整理（距离、耗时、台阶），范围缩到3个景点、1–2条路线，反复测同一场景
3. **调研和叙事容易被开发挤掉**：开场后6小时内必须完成访谈

| 风险 | 备用方案 |
|---|---|
| 现场网络不稳 | 手机热点，提前录好演示视频 |
| 户外语音识别差 | 提供按键或文字备用输入 |
| 设备联调卡住 | 手机端完整演示，设备作展示道具 |
| 访谈显示不愿带玩偶 | 改为挂件形态，或回到手机端精灵 |
| 固件与自定义箭头冲突 | 箭头放手机网页，设备只做语音与表情 |

## 十二、关于硬件的补充说明

- M5Stack StopWatch：1.75寸AMOLED圆形触控屏、麦克风、扬声器、震动电机、450mAh电池、直径52毫米、重39克；官方提供小智固件的烧录教程
- **用小智固件**：语音现成，但屏幕上的箭头和震动指令需改固件，工作量增加
- **自写固件**：箭头、震动容易控制，但语音识别、合成和对话要自己对接，工作量大
- 建议：小智负责语音和表情，导航与地图放手机端；有余力再尝试加箭头
- NFC需外接模块；**兼容性和现成示例尚未核实**，赛前必须先查
- 该板子较新，社区教程少，必须赛前跑通
- 手表类设备：成品智能手表基本无法改造；可考虑“挂件或手腕形态”的开发板

**对硬件同学的要求**：会烧录和调试ESP32类开发板；能跑通小智；懂Wi-Fi、WebSocket、HTTP；会查资料排错；加分项：Arduino或C++、I2C外设接入、外壳动手能力。不需要画PCB。

## 十三、路演结构

1. 访谈发现：用游客原话开场，讲清痛点
2. 方案：一句话介绍枫叶精灵
3. 现场演示：一次“时间不够，当场重新规划”
4. 落地性：真实路线数据、低成本、可复制到其他景区
5. 下一步：IP周边、景区合作、租借模式

**三件保险**：备用演示视频、手机热点、备用开发板；路演前至少完整彩排两遍，包含网络出问题的情况。
