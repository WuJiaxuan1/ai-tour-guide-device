# 网页行程与小智语音共享上下文方案

日期：2026-10-30。状态：设计方案，未实现、未部署。

## 目标与推荐架构

游客在网页选择景点、确认路线，再向 StopWatch 提问，小智能查询本次行程和已有景点知识库作答。

推荐继续使用小智官方语音云端；网页、业务后端、知识库和 MCP 工具服务部署在项目 VPS。MCP 通过现有接入点主动连接小智，按需查询行程。无需为第一版迁移语音服务或修改地图渲染。

```text
手机网页 ──保存选择/路线/有效位置──> 项目后端与数据库
                                        ↑
                                  MCP 只读查询工具
                                        ↕
StopWatch <──语音对话──> 小智云端 ──工具调用──┘
```

## 本次代码检查确认的现状

检查的是本地 integration/web-server-stopwatch 分支，不表示已对公网部署版本做一致性核验。

- frontend/src/Qixia.jsx 使用浏览器 localStorage 保存部分状态；网页问答时把 route、位置交给 askAgent。
- frontend/src/agent.js 把 sessionId、messages、context.routeIds、context.location 发给 /api/knowledge/chat。
- backend/src/server.mjs 的上述接口读取最后一条消息并调用 knowledge.chat；未建立持久化的游客行程与手表绑定。
- 当前 knowledge.chat 使用规则/别名查询，不能因为请求含 sessionId 就认定已经实现共享会话或身份认证。
- 本地 mcp-local-demo 的知识工具能查询静态12景点资料，尚不能读取游客实时选择、路线或当前位置。
- 架构文档中的 trips、next-stop 等路径是设计，不是当前全部可用的接口。

## 两种数据要分开

1. 景点知识：介绍、历史、看点、资料核验限制；多位游客可共用。
2. 游览上下文：某位游客的选择、顺序、当前查看景点、确认路线、进度、有效位置；必须按会话隔离。

仅上传知识库不会让小智获知网页选择。仅部署在同一台服务器也不会自动共享上下文。

## 业务数据设计

后端创建 tripId 并关联经过验证的网页会话。会话凭证是认证依据，tripId 是资源编号；不能仅凭知道 tripId 就查询或修改他人行程。

记录至少包括：

- selectedPoiIds：选择集合，与实际道路路线分开。
- orderedStopIds：游客当前确认的站点顺序。
- focusedPoiId：网页正在查看的景点；不等于游客实际到达地点。
- routeId / routeRevision / routeStatus：正式路线快照及状态；未生成时明确 unavailable。
- currentStopIndex / visitedPoiIds：已经确认的进度；仅有选择时不能推断下一站。
- location：坐标系、坐标、精度、原采集时间和有效状态；过期位置不当成实时位置。
- contextRevision / updatedAt：防止旧请求覆盖新选择，说明数据新鲜度。
- deviceBinding / voiceBinding：网页行程与导航设备、语音工具实例的关联。

建议复用既有导航方案的 tripId、设备绑定和路线版本，不再独立创建另一套语音行程。

前端变更选择后自动保存，短暂合并连续操作；显示“同步中 / 已同步 / 同步失败”。等待服务器确认后才能宣称已同步。相应的取消、重排、清空也要同步。

## MCP 工具（拟新增）

| 工具 | 功能 | 约束 |
| --- | --- | --- |
| get_current_trip | 查询本次选择、顺序、当前查看景点、路线状态 | 服务端根据绑定确定行程，不让模型任选游客ID |
| get_next_stop | 返回已确认路线上的下一站和已有距离/耗时 | 未开始、进度未知、路线未生成时明确说明；不现编距离 |
| get_current_location | 返回有效位置及对应景点候选 | 位置过期或精度不足时不声称“你就在这里” |
| get_attraction_guide | 查询指定景点讲解资料 | 复用现有知识工具，保留核验限制 |

第一版仅实现 get_current_trip 与已有 get_attraction_guide，其他工具依赖导航进度/GPS阶段。

角色说明增加：涉及“我的路线、我选了什么、下一站、当前行程”时重新查询工具，不靠旧聊天内容猜测。更新网页后，以当前服务端版本为准。

MCP 是按需查询。网页修改会更新业务数据库，不意味着自动插入小智当前对话、更不意味着手表立即播报。主动到点播报与语音反向修改路线留待后续。

## 必须先解决身份对应

现有 mcp_pipe.py 转发 MCP 消息，没有替业务建立浏览器游客与说话设备的对应。不能假设云端工具调用自动携带可验证的设备ID。

### 首版：单手表演示

- 一个专用测试智能体/接入点、一个 MCP 实例，明确只服务这一台测试手表和一个当前行程。
- 网页经带认证的短期配对流程将行程绑定到该实例；不要求模型识别或猜测 tripId。
- 同一时刻只允许一个有效绑定；解除或结束后工具返回“尚未连接行程”，不能继续返回上一位数据。
- 如果多人或多台手表共享这个智能体，不能把这套演示方案直接作为多人方案。
- 演示版可用服务器生成的短期配对页/码，不要求首轮修改固件显示码；导航正式配对阶段再统一体验。

### 多手表：单独验收后再开放

优先评估设备端 MCP 工具：云端调用当前设备的工具，由设备使用自己的凭证查询其绑定行程。此路径需要修改固件，并验证当前版本的设备端 MCP 能力、超时与并发行为。

另一方向是每台设备独立语音智能体/接入点/工具作用域，前提是平台支持所需数量与管理能力。没有可信设备上下文时，不用“全局最近一次行程”来代替隔离。

## 是否把网页部署到“小智服务器”

- 当前使用的官方云端与 MCP 接入点不提供我们已有的服务器登录/网页部署权限；MCP 接入点是工具通信通道，不是网页托管入口。不能仅凭接入链接上传部署前端。
- 可以考虑在自己的 VPS 自建小智兼容语音后端，与网站分别运行、通过反向代理提供服务。但需要额外配置语音识别、大模型、语音合成和设备服务地址；资源与现有功能兼容性也要测试。
- 自建语音后端和网站放在同一台机器，仍需要上述业务接口、会话关联和权限控制。
- 当前推荐不迁移语音服务：先让官方小智通过 MCP 读取现有 VPS 的业务数据。

## 分阶段验收

| 阶段 | 我实现 | 用户验收 |
| --- | --- | --- |
| A 网页保存 | 行程接口、存储、选择/取消/顺序同步及真实状态 | 添加明镜湖、舍利塔，刷新仍在；取消后确实保存 |
| B 单表绑定 | 一个测试智能体与一个行程绑定、解除、过期处理 | 连接后显示绑定状态；解除后小智不再读取旧行程 |
| C 小智读选择 | get_current_trip 与景点讲解工具组合 | 问“我选了哪里”；网页删一站后再问，回答随之改变 |
| D 路线与位置 | 接导航计划的路线、进度、有效GPS | 正确回答下一站；停止定位后明确位置已过期 |
| E 服务器常驻 | 部署MCP、重连、服务重启与健康检查 | 关闭开发电脑，手表仍能查询；服务重启不串行程 |

至少测试两个独立浏览器会话；未绑定的会话不能读取或覆盖已绑定行程。服务不可用时小智不能声称已查到最新选择。

当前未登录 VPS、未修改线上网站，未改手表固件。部署前需要服务器同学完成公钥授权并确认账号/端口，连接时仍需核对主机身份。
