# 网页 → 服务器 → StopWatch：分步开发与验收方案

更新：2026-10-30。

**本文是开发计划，不表示下列新功能已经实现。正式使用链路不安装、不运行 Android App。**

前端基线：`origin/release/frontend-0.4.0`，提交 `91317a5`。硬件基线：已验收 P8-test02，提交 `a9789fe`。本地集成分支：`integration/web-server-stopwatch`，从指定前端分支创建。后续在该分支整合硬件提交并开发；不直接向前端发布分支或 main 写入改动。

## 1. 最终使用场景

1. 游客给 StopWatch 配网。可以连接手机热点，也可以连接其他可上网的 Wi-Fi。
2. 手表主动连接项目服务器，显示短时有效的连接码。
3. 游客打开手机 HTTPS 网页，输入连接码，确认这次游览要连接的设备。
4. 网页请求手机定位权限。游客选择并确认路线，点击“开始手表导航”。
5. 服务器保存路线，处理手机定位，准备当前位置附近的地图块。
6. 手表从服务器取得地图、路线和位置，显示与网页相同的道路路线。
7. 游客行走时，手表移动地图窗口、提前下载下一块地图，并把已走路线改为已走色。
8. 游客可切换网页内部的探索、问枫枫、路线页；导航会话继续定位。手表可切到语音页进行小智对话，再返回地图页恢复最新状态。
9. 游客结束导航或解除连接后，服务器停止该会话的位置分发。下一位游客不能收到上一位的路线或进度。

**纯网页的使用边界：第一版要求手机网页在前台、屏幕保持亮起。** 可以请求 Screen Wake Lock，并在回到前台时重新申请，但浏览器不支持、系统收回权限、切到其他 App、切后台或锁屏后，都不能保证继续提供 GPS。PWA 不消除这个限制。位置失效时手表必须提示暂停，不能假装仍在实时导航。

该限制不影响使用网页本身的多个页面，但需要把定位会话放在全局层，而不是跟随当前页签销毁。

## 2. 已确认的默认参数

下表来自现有 App 源码默认值及 P8-test02 固件，不推测某一部手机偏好设置里后来保存的自定义值。新链路以这些默认值作为基线，不把此前验收时临时调的16.0或绿色测试配色当默认。

| 项目 | 沿用值 | 新链路实现位置 |
| --- | --- | --- |
| 地图缩放 | **14.0** | 服务端统一地图配置 |
| 地图文字 | **隐藏**，`CLEAN` | 地图服务样式；实现前必须验证支持 |
| 地图方向 | 北朝上，倾角0，不随行进方向旋转 | 地图生成和手表绘制 |
| 底图类型 | 普通二维地图，不启用3D建筑、室内地图、实时路况 | 地图服务 |
| 地图块 | **480×480源像素** | 服务端生成、手表缓存 |
| 可见窗口 | **240×240源像素** | 手表在地图块中移动窗口 |
| 屏幕 | 466×466圆屏，窗口铺满屏幕 | 沿用固件 |
| 地图编码 | RGB565，小端；沿用 QMAP v3/type3 | 服务端编码、固件解析 |
| 地图颜色内容 | 以地图服务返回的道路等底图为准，不重新发明地图样式 | 服务端地图提供器 |
| 未走路线 | 粉色 `#FF4FB4` | 路线图层 |
| 已走路线 | 灰色 `#888888` | 路线图层 |
| 当前定位点 | 蓝色 `#008CFF`，圆形 | 手表绘制 |
| 终点 | `#FFB547`，黄色方形 | 手表绘制 |
| 描边 | 白色 `#FFFFFF` | 手表绘制 |
| 路线线宽 | **8个手表屏幕像素** | 手表绘制 |
| 预取边距 | 60源像素 | 服务端复用现有 MapChunkPolicy 规则 |
| 地图窗口移动动画 | 320ms | 沿用固件 |
| 左右页面切换动画 | 240ms | 沿用固件 |
| 地图生成/预取最短间隔 | 沿用原 App 的5秒节流，首图立即开始 | 服务端调度；不是每5秒强制重画 |
| 定位显示有效期 | 15秒 | 全链路计算位置年龄，固件作最后检查 |
| 定位点精度门槛 | 有效精度≤50米 | 沿用地图显示规则 |
| 已走进度精度门槛 | 有效精度≤25米 | 服务端移植进度算法 |

原实现支持缩放13～18、步进0.5、线宽2～16；本次先固定上述默认值。调参入口可留在维护页，不先增加游客操作负担。底图控制和路线控制分开；不要把路线烘焙进地图图片，以免每次走动都要重发大图。

### 2.1 “同样缩放”需要实际校准

不同地图接口对 zoom、像素密度和 scale 的解释可能不同。不能只把参数填14，就认定与原 App 的地理范围相同。

以既有已验收的地图块地理边界与480源像素的对应关系为参照，检查相同中心附近的两处道路/地标在地图中的距离。传给固件的边界必须描述实际图片区域，不能一边截取或缩放图片、一边沿用另一张图的边界。路线、定位和地图统一用 GCJ-02，按当前投影方式对齐。

隐藏的是地图文字，不是擦除服务要求保留的署名。当前服务端静态图接口是否支持无文字样式及同等比例尺，尚待验证；这是前置验收项，不承诺未经验证的地图服务效果。

## 3. 各部分负责什么

| 模块 | 工作职责 |
| --- | --- |
| 手机网页 | 展示/选择路线、确认绑定设备、获取手机 GPS、上传位置、开始/暂停/结束导航、显示真实同步状态 |
| 服务器 | 保存路线快照和设备关联、转换坐标、匹配路线进度、准备并缓存地图块、下发数据、处理版本及回执 |
| StopWatch | 主动连接服务器、下载并验证数据、显示地图窗口/路线/位置/已走颜色、上报设备状态、保留小智语音 |
| 高德或选定地图服务 | 提供地图与实际道路数据；不能由模型编造折线 |
| 小智云端 | 沿用原语音会话；本轮不承担地图块传输，也不默认与网页共享业务会话 |

热点只提供互联网连接。手表不需要开放公网端口，服务器也不向手机热点里的私网 IP 主动发 HTTP 请求。手机和手表只要分别能访问服务器即可；不以“必须同一热点”作为服务器架构限制。

## 4. 通信和数据设计

### 4.1 两条传输通道

- 网页 → 服务器：HTTPS。发送路线选择、位置和导航控制。原生 GPS 回调来得不规律时，只上传最新有效点，不制造虚假的每秒定位。
- 手表 → 服务器：手表主动建立连接。最早的连通测试用 HTTPS 查询；持续导航采用 WSS 收取位置、控制、更新通知，地图大文件用 HTTPS 下载。

小智继续使用原语音连接。新增导航连接不复用小智 token，不改变原绑定身份。增加连接后必须实测 TLS 内存、重连和语音恢复，不以 Flash 剩余容量代替运行内存检查。

### 4.2 消息频率与过期

- 有新 GPS 时目标约每1～3秒上传一次，初始节流目标2秒；这是处理目标，不是保证手机每2秒产出定位。
- 只有一个正在上传的位置请求；过慢时保留最新待发点，丢弃过时队列，不把一分钟前的位置逐个播放给手表。
- 上报序号、定位采集时间、精度、坐标系、位置年龄；速度/方向允许缺失，缺失时不用前向预测。
- 网页、服务器、手表各自检查序号和位置年龄。服务器转发、缓存命中、设备重连不能重置原始 GPS 的年龄。
- 不直接比较三台设备的单调时钟。服务器累加接收后的驻留时间，手表叠加传输/接收后的时间；对异常时间、过高延迟采用保守过期处理，并测试时钟偏差。
- 超过15秒没有新有效位置：隐藏旧定位点、停止推进进度，保留地图和已确认的已走前缀，显示“定位已暂停/等待定位”。
- 地图只在缺图、覆盖不足或进入预取范围时生成，不随每条 GPS 重发。480×480 RGB565 像素体约460800字节，连同现有头部约460896字节。

### 4.3 独立保存三个版本概念

- `tripId / routeId / routeRevision`：游客行程和确认的路线版本。
- `deviceSession / bootId / transferRevision`：设备本次连接和手表传输版本。
- `mapFrameId / positionSeq / routeGeometryHash`：当前地图帧、位置序号及用于进度计算的折线版本。

现有手表协议的 revision 连颜色变更都会增加，不能直接等同网页的路线 revision。服务器保存两者映射。首次绑定、重复取任务、断线恢复不能被当成重新规划；明确替换路线时才清旧进度。解绑定/结束导航的控制序号必须能压过延迟到达的旧任务。

### 4.4 状态与确认

网页状态分别表达：等待设备、等待 GPS、等待地图、服务器已保存、手表已接收、正在导航、暂停、错误。服务器保存成功不等于手表收到。

现有 P8 ACK 是共享状态接收确认，不是屏幕刷新确认。先沿用“手表已接收”；如要显示“手表已显示”，固件需在实际安装到显示对象后补一个 `applied` 回执，不能只改网页文案。

### 4.5 路线数据约束

- 网页只有景点列表、算路失败或推荐结果 `routeReady=false` 时，不能发送“正式导航路线”。
- 接收并保留已确认的实际道路折线；不能仅取最后一个终点重新算路，不能用直线连景点代替道路。
- 网页 GeoJSON 点为 `[lng, lat]`，QRTE 为纬度、经度。明确转换字段顺序，不重复做坐标偏移。
- 网页最多20000点，手表最多2048点。移植已有 RDP 简化策略，保存简化后几何，进度算法和手表都使用这一份。过度复杂无法满足限制时拒绝，不能截尾。
- 现有后端 `body()` 限制16KB，不能直接往同一路径塞20,000点大JSON。优先由后端保存它自己生成的路线快照，网页提交 routeId/revision；确需上传折线时使用单独、有界的接口并验证大小。
- 当前路线缓存仅是短期内存缓存，不足以承担导航任务。导航路线、设备关联和进度需有明确的持久化与恢复策略；建议以 SQLite 保存小规模会话/任务，地图文件另存有界缓存。
- 正式路线策略沿用团队确定的预设匹配和离线矩阵；本轮不扩大旧实时最短路算法。最终预设尚未交付时，先用已生成的真实道路路线验证通信。

## 5. 地图来源：先验证，再集成

去掉 App 后，原来的 `PhoneMapRenderer` 不能原封不动在 Node 上运行。需要实现一个服务端 MapProvider，输出：地图字节、实际 GCJ-02边界、尺寸、样式、缩放配置及内容校验值。

按以下顺序评估：

1. **官方支持的静态地图/服务端图片能力**：先核实权限、可用样式、像素尺度、无文字效果和地理边界。达到默认显示要求后，作为首选。
2. **服务端地图渲染**：若第一种不能实现隐藏文字和比例尺，再验证官方支持的渲染方式。可能需要独立渲染进程；先测启动、首图、地图完整性、资源占用，再决定使用。不能把网页截图一定可用当作前提。
3. **景区预制地图块**：若实时方案达不到要求，向用户明确提出限定景区的备选。地图需具备来源与正确地理参考；限定范围会影响景区外测试，不能静默切换。

如果首选不支持隐藏文字，不以保留文字/擦除图片中的字冒充完成。此时保留默认需求，给出第二种方案的验证结果和成本供选择。

所有提供器都必须输出同一数据格式。这样地图来源的变化不要求重写 GPS、路线分发和手表页面。

## 6. 分步开发：每阶段均有可检查成果

### P9-0：固定基线、建立分支与通信契约

开发工作：

- 在 `integration/web-server-stopwatch` 集成指定网页分支和已验收硬件代码，保持现有工程结构，不复制整套版本目录。
- 核对提交与配置，把上述默认参数集中成服务端配置；不会从 App 读取运行数据。
- 定义设备会话、GPS消息、路线快照、地图下载和回执契约，并准备合成数据样例。
- 明确配对/位置/路线接口与现有网页 API 的关系；不把本计划的接口当成已经上线。

交付：接口说明、默认参数文件、分支基线记录。

验收：现有网页仍可构建；硬件板级代码和改版配网组件完整保留；样例能表达新路线、取消、过期位置和旧版本。

### P9-1A：服务端底图可行性验证（前置门槛）

开发工作：

- 针对一处确定位置，在服务端生成地图，验证默认14.0对应的地理覆盖、无文字、北朝上、480×480。
- 建立地理边界计算、RGB565LE编码与校验流程。
- 在测试预览上叠加已知坐标点和真实道路折线，核对位置、方向与比例尺。先通过软件验证，再交给后续手表首图测试。

交付：服务器生成的样图、边界数据、与现有比例尺的对比记录、所选服务能力说明。

你检查：显示范围是否与已验收默认效果接近，文字是否隐藏，道路/定位是否重合。此阶段可以在电脑预览，不安装 App。

通过条件：底图满足基线。未通过时只继续独立通信开发，不宣布地图方案完成，也不开始大规模重构。

### P9-1B：设备上云与配对（可与底图验证独立推进）

开发工作：

- 固件增加导航云连接模块，Wi-Fi连通后主动请求服务器。先用 HTTPS 完成注册、心跳、查询和明确的错误提示。
- 实现短时、一次性连接码与确认流程。设备标识不是密码；用设备自己的凭据识别会话，服务器校验网页与设备的关联。
- 网页新增连接设备入口、已连接设备名称、断开入口。
- 让浏览器会话/设备会话互相隔离，避免多位游客发给同一块表时无提示覆盖。

交付：新固件、配对网页、设备会话后端。

你检查：不开 App，只用网页连接成功；输入错误/过期连接码明确失败；手表断网时网页显示离线；重新联网恢复。

通过条件：至少一台真机完成配对、断开、重连；软件测试验证两个会话不串线。

### P9-2：网页 GPS → 服务器 → 手表

开发工作：

- 将现有 `useVisitorLocation` 改为导航会话控制。开始导航后，在网页内部切探索/路线/问枫枫时不停止。
- 保留浏览器权限和 HTTPS检查，新增目标2秒节流、最新点覆盖、序号、时间和精度处理。
- 将现有坐标转换接入统一位置管线，评估高频调用成本和额度，避免一个位置重复转换；不能简单把原10秒限流删掉就当完成。
- 手表先在维护状态区显示位置、精度、更新年龄，不等待整套地图完成。
- 位置过期、拒绝权限、网页隐藏和恢复均有对应状态。

交付：网页位置采集模块、服务端位置管线、可显示接收状态的固件。

你检查：前台行走后数值更新；网页内部切页继续更新；关闭定位或切手机后台后，15秒有效期到期提示暂停；回前台重新获取真实定位后恢复。

通过条件：没有重复点推进、乱序覆盖、重连刷新旧位置年龄或游客间串位置。此阶段不将模拟定位通过写成室外GPS验收。

### P9-3：云端地图块 → 手表巡航

开发工作：

- 服务端根据最新位置选择/生成地图块；手表 HTTPS 下载完整 QMAP，再经现有验证、共享状态及显示流程安装。
- 小数据控制与地图下载分开；下载期间仍允许位置更新，避免在显示线程执行网络请求。
- 复用480地图块、240窗口、60预取边距、320ms窗口动画和边缘限制。
- 移植前向预取：有可信方向、速度≥1.4m/s、精度≤25m时，预留约20秒行进距离且最多40源像素；否则以当前位置取图。
- 新块完整验证、安装成功前保留旧块；下载失败/地图提供器超时不清空屏幕。

交付：无 App 的巡航固件、服务端地图生成/缓存/调度模块、网页地图状态。

你检查：用网页定位，手表地图铺满圆屏、文字隐藏、范围为默认效果；走动时点尽量居中，地图移动；走出原图范围前换块；地图请求失败时旧图保留。

通过条件：路线未接入也能完成一次室外巡航；图块下载不阻塞整个界面。此阶段才确认服务端地图真正达到硬件显示要求。

### P9-4：网页路线 → 手表路线与已走变色

开发工作：

- 网页只将已经生成、用户确认的道路路线交给导航会话。
- 服务端保存路线快照、简化几何并编码 QRTE；底图与路线分开传输。
- 将 `RouteProgressTracker` 的已验收规则移植到服务端：精度门槛、连续性限制、单调已走前缀、重复GPS忽略、回走不回退。
- 保留原默认配色和8像素线宽；默认样式从服务器集中下发，不依赖手机旧偏好。
- 区分真正换路线与重连重发。新路线明确清零，重连恢复原已走进度，过期任务不得覆盖当前版本。

交付：网页“开始手表导航/更换路线/结束导航”、后端路线和进度模块、配套固件。

你检查：网页与手表道路走向一致；实际沿路线走动后粉色已走部分变灰；回走不重新变粉；换块不丢分界；更换路线按新路线重新开始；取消后不被旧请求恢复。

通过条件：网页/服务器/手表对同一简化路线的游标一致，重复请求不会反复重置进度。

### P9-5：多景点、起点不在身边与往返处理

开发工作：

- 网页选择的是多景点行程，游客不一定站在入口。第一版先明确“去入口后开始”与“预览路线”的区别，不把距离当前用户很远的路线强行染色。
- 当前 P8 进度算法只在上一进度附近匹配，不能无条件跳到远处路段。如果允许中途加入，需用户明确选当前路段并建立新的进度起点，不能自动宣称前面都已走过。
- 当前网页 legs 主要是距离/时间，不含可靠的折线段索引。增加每段 geometry 或原始折线范围；简化时保留路段边界，再建立点索引映射。
- 加入服务端当前路段、下一站、手动到访/跳过。GPS通过某点不自动等同游客完成参观。
- 往返、重叠路段按照行程段匹配，先以手动确认推进段号，避免把去程错误匹配到返程结尾。
- 暂不做转向播报和偏航自动重算；如后续需要，单独开阶段验收。

交付：多站行程状态及网页当前段/下一站显示；必要的手表提示小改。

你检查：选择相同入口出口、至少两个中间景点；确认下一站顺序；回头路不提前完成；远离路线时提示等待/偏离；手动跳过后进度含义正确。

通过条件：在至少一条多站真实路线中不出现串段和错误全程变色。最终预设路线/矩阵缺失时不能将测试路线冒充正式路线。

### P9-6：持续连接、恢复与小智回归

开发工作：

- 从早期查询机制升级为 WSS 位置/控制通道，地图仍走HTTPS；浏览器可先查询状态，之后按需要增加事件通道。
- 心跳、连接超时、指数退避、重连状态快照、最大待处理消息数与地图并发限制。
- 导航不活动时降低通信；地图页切到语音页时暂停大图下载，并回报页面状态，返回后恢复最新地图/路线，不回放全部历史GPS。
- 检查新连接对语音、唤醒、PSRAM/SRAM、堆碎片和CPU的影响。保留开机配网、音量85、左右键/滑动切页。
- 网页支持的设备上请求屏幕常亮；权限被收回时显示提示。断网时保留手表现有图层；没有新GPS就停止推进，不能承诺联网中断后仍能完整导航。

交付：稳定连接版本、错误状态表、恢复测试记录。

你检查：连续前台导航至少30分钟；切语音页对话再返回；热点断开再接入；手表重启；网页刷新；锁屏/后台与回前台；各过程无误显示、无反复清零或死机。

通过条件：给出实际重连时间、定位年龄、地图传输时长与资源情况；不把性能目标当测量结论。Zenfone 10先验收，iPhone/微信浏览器另列兼容结果，不自动宣称全部支持。

### P9-7：部署、联调与交接

开发工作：

- 补充部署环境变量样例、数据库初始化、地图缓存目录、WSS反向代理、HTTP下载及超时配置。
- 核对现有后端按 remoteAddress 统一限流的实现。Nginx代理下不能让所有游客共用同一个导航限流桶；按已验证会话/设备限流，正确配置可信代理。
- 实测ESP32的服务器证书信任与时间初始化；不关闭证书验证。手机浏览器能访问不代表固件TLS必然成功。
- 在有明确部署范围和所需服务器资料后，按项目SSH操作记录要求部署。该方案不假设队友机器的SSH密钥已在本机可用。
- 更新源码、变更记录、部署步骤、验证结果和回退说明，推送集成分支供团队审阅。生产发布单独保留旧网站和已验收固件回退路径。

交付：可访问的新网页/后端、配套固件、使用说明、测试记录和代码合并请求。

验收：关闭/不安装 Android App，按第1节从头完整操作；网页、GPS、服务器和手表组成闭环，原小智语音功能可回归。

不在此处承诺固定完工日期：地图服务能力、服务器配置、TLS和现场GPS效果会影响进度。完成P9-1A/1B后再给出更可靠的排期。
